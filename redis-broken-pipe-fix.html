Fixing Error 32 … Broken pipe in credit-admin-tool

scrp-chat / Open WebUI deployment · diagnosed 2026-11-14

1. Symptom

Invoking the credit-admin-tool in chat fails with:

Error querying credit usage: Error 32 while writing to socket. Broken pipe.

The rate-limiter filter, by contrast, continues to work (credit keys kept receiving writes, and rate-limiter commands zcount, eval, zrangebyscore were observed running live during diagnosis).

2. Diagnosis

2.1 What was ruled out

  • Valkey server down or unhealthy. BGSAVEs were completing successfully right up to the moment of diagnosis; the server answered PING with PONG; rejected_connections:0; 53 of 10,000 client slots in use.
  • The "(unhealthy)" container badges. These are an artifact: docker exec has been broken host-wide on scrp-control-2 since ≈ Nov 6 (the healthcheck exec died on an AppArmor error, FailingStreak = 713,689 ≈ 8.3 days of once-per-second failures). The healthchecks run via exec, so they fail while the services themselves run fine.

2.2 Root cause

Valkey's timeout is set to 1800 seconds. The server closes any non-pubsub connection that has been idle for more than 30 minutes.

This bites the admin tool specifically because of how the two components use their connections:

Rate-limiter filtercredit-admin-tool
FrequencyEvery chat requestOnly when invoked in chat (hours/days apart)
Pool idle timeNever approaches 30 minRoutinely exceeds 30 min
ResultConnections stay aliveValkey reaps the pooled socket between invocations

Both components create their client once and reuse it (self._redis, built with a bare redis.from_url(...)). When the admin tool is invoked after a long gap, redis-py writes the command into the already-closed socket → Error 32 … Broken pipe. This is a client-side view of the server having closed the connection, not a server crash.

2.3 Corroborating evidence from CLIENT LIST

  • Pubsub connections (flags=P) survive despite idle far above 1800 s — pubsub clients are exempt from the timeout reaper, exactly as expected.
  • Every normal connection showed idle below 1800 s — consistent with active reaping at that threshold rather than random drops.
  • tcp-keepalive=300 does not mitigate this: Valkey's timeout is an application-level idle counter reset only by commands, not by TCP keepalive probes.

3. The fixes

3.1 Temporary / immediate fix (runtime)

Run on scrp-control-2 (the bridge IP of the redis-valkey container was 172.18.0.2 at diagnosis time; re-derive it with docker inspect if it has changed):

IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' redis-valkey)
redis-cli -h $IP CONFIG SET timeout 0

This takes effect immediately for the running Valkey — the server stops reaping idle connections — but does not survive a container restart if the 1800 value comes from a config file or startup command.

One-time retry note: the admin tool's pool still holds its already-dead socket. If the first invocation after the fix fails once more, simply invoke it again — redis-py discards the broken connection and the next call gets a fresh one.

3.2 Permanent fix

Server side — persist the setting. Find where 1800 comes from and make 0 the persisted value:

# Option A: persist current runtime config to the mounted conf file (if writable)
redis-cli -h $IP CONFIG REWRITE

# Option B: inspect where the value is set, then edit it there
docker inspect -f '{{json .Config.Cmd}}' redis-valkey     # startup command flags
docker inspect -f '{{json .Mounts}}' redis-valkey         # mounted valkey.conf

Background: Valkey's own default for timeout is 0 (never reap), so 1800 was configured deliberately somewhere. Idle-connection hygiene is not needed here — only 53 of 10,000 client slots are in use — so setting it to 0 permanently is safe. After editing a mounted conf, restart the valkey container to confirm the setting sticks.

Client side — harden both components (recommended, optional). Even with timeout 0, any future idle reaping or transient connection loss would resurface the same error, because both files build their client with bare defaults:

self._redis = _redis.from_url(self.valves.redis_url, decode_responses=True)

Patch _get_redis() in both credit-admin-tool.py and rate-limiter.py:

self._redis = _redis.from_url(
    self.valves.redis_url,
    decode_responses=True,
    socket_keepalive=True,      # OS-level keepalive on pooled sockets
    health_check_interval=30,   # PING before reuse; dead conn detected & reconnected
)

health_check_interval is the load-bearing option: on the first command after ≥ 30 s of pool idle time, redis-py silently issues a PING, detects a dead connection, and reconnects — the failure becomes invisible instead of surfacing as a broken pipe. Per repo conventions this patch would be a version bump in both files' frontmatter, followed by re-pasting them into the Open WebUI Workspace (editing reloads the module).

4. Verification

# 1. Setting took effect
redis-cli -h $IP CONFIG GET timeout          # expect: 0

# 2. Ledger is current (newest credit record vs. now)
for k in $(redis-cli -h $IP --scan --pattern 'oi-rate-limiter:*:credits'); do
  redis-cli -h $IP ZRANGE "$k" -1 -1 WITHSCORES | tr '\n' ' '; echo "  $k"
done | sort -k2 -n | tail -3
date +%s                                     # scores within minutes = live

Then invoke the credit-admin-tool in chat — possibly twice, per the retry note above — and confirm usage queries return normally.

5. Side findings (unrelated to this bug, worth tracking)

  • docker exec broken host-wide since ≈ Nov 6 — every exec dies on "Could not check if docker-default AppArmor profile was loaded" (ExitCode: -1). Likely a kernel/AppArmor update regression; check dmesg | grep -i apparmor and recent package history. This is also the sole reason both containers show "(unhealthy)".
  • Open WebUI is now v0.12.5 (container open-webui-v0.12.5, created 11 days before diagnosis), not the v0.12.3 previously recorded. Version-specific behavior notes (Anthropic conversion path, outlet-filter defaults) should be re-verified against the v0.12.5 source and the Postgres function/tool tables.
